# wharf-web

The **web auth flow** for [Wharf](https://github.com/Janne6565/wharf-tui) — a local-first,
zero-knowledge SSH-fleet manager. This app is where you create an account, save your
one-time recovery code, pair your terminal, sign in, and reset your password via recovery
code. It talks to [`wharf-backend`](../wharf-backend) and is byte-compatible with the
[`wharf-tui`](../wharf-tui) vault format.

Everything sensitive happens **in your browser**: your master password, the derived keys,
the vault plaintext, and the recovery secret never leave the device. The server only ever
receives a derived `authKey`/`recoveryAuthKey` (which it bcrypt-hashes) and the opaque
ciphertext vault blob.

## Stack

TypeScript · **TanStack Start** (Vite, file-based routes, `beforeLoad` guards) · React 19 ·
TanStack Query · Redux Toolkit (session state) · Tailwind CSS v4 · react-hook-form + Zod ·
react-i18next (typed resources) · **Orval** (generated API client) · **Bun** · Biome ·
Vitest. Crypto: **hash-wasm** (argon2id, p=4), **WebCrypto** (SHA-256 + HKDF),
**libsodium-wrappers** (XChaCha20-Poly1305).

## Running against the backend

```bash
bun install

# 1. start the backend (Spring Boot, H2 dev profile) on :8080
cd ../wharf-backend
JAVA_HOME=$(/usr/libexec/java_home -v 21) ./mvnw spring-boot:run \
  -Dspring-boot.run.profiles=dev
# (or run the prebuilt jar: java -jar target/wharf-backend-*.jar --spring.profiles.active=dev)

# 2. start the web dev server on :5173 (proxies /api -> :8080)
cd ../wharf-web
bun run dev
```

Open http://localhost:5173. The Vite dev server proxies `/api` to `http://localhost:8080`
(override with `VITE_DEV_API_TARGET`). In production, point the client at the API with
`VITE_API_URL` (see `.env.example`).

## Screens

`/signup` → `/welcome/recovery-code` → `/device`, plus `/signin` and `/recover`. Route
access is enforced in TanStack Router `beforeLoad` guards (never in components); `/`
redirects to `/device` (authed) or `/signin`. The auth screens are fully client-rendered
(`ssr: false`) because the crypto is browser-only; the root shell still renders on the
server so a future SSR/SEO landing page can be added.

## Crypto model (summary)

All derivation is client-side and matches wharf-backend's contract and wharf-tui's vault
defaults:

| Value | Derivation |
|---|---|
| `masterKey` | `argon2id(password, salt = SHA-256(lowercased,trimmed email)[:16], t=3, m=64 MiB, p=4, 32B)` |
| `authKey` | `base64(HKDF-SHA256(masterKey, "wharf/auth/v1", 32B))` — the login credential |
| `recoverySecret` | 25 random bytes → 40-char Crockford base32 code (shown once) |
| `recoveryAuthKey` | `base64(HKDF-SHA256(recoverySecret, "wharf/recovery-auth/v1", 32B))` |
| `vault` | **WHARFV** binary (magic `WHARFV`, v1, 218-byte LE header, argon2id, password + recovery unlock slots wrapping one DEK, XChaCha20-Poly1305 body with the header as AAD), base64-encoded |

argon2id runs through **hash-wasm** specifically because the contract needs parallelism 4
(libsodium.js hardcodes p=1). The `src/crypto/` module is a byte-for-byte port of the Go
`internal/vault` package; a committed fixture generated by the Go code
(`src/crypto/__fixtures__/vault-fixture.json`) is unlocked by the TS implementation via
both slots in `src/crypto/fixture.test.ts` to prove compatibility.

### Auth / tokens

The short-lived identity (access) token lives only in memory; the long-lived refresh token
is an httpOnly cookie. The Orval `customInstance` (`src/api/axios-instance.ts`) attaches the
Bearer token and silently refreshes on a 401. On app load the root route runs a one-time
silent refresh so route guards see a resolved session.

## Build output / deployment

`bun run build` produces a **Nitro Node server** in `.output/` by default (run it with
`bun run start` / `node .output/server/index.mjs`) alongside the client assets — this is
what lets a real SSR landing page be added later. Because the auth screens are client-only,
the app can equally be deployed as static assets (Nitro supports static/prerender presets)
behind any host that proxies `/api` to the backend; only the (future) landing page would
need the Node server for SSR.
